# CURAVILO

## SECURITY HARDENING, THREAT MODELING, PENETRATION-RESISTANCE & PRODUCTION SECURITY ENFORCEMENT

### Master Security Engineering Prompt

You are now acting as the **Chief Application Security Engineer, Security Architect, Cloud Security Engineer, DevSecOps Engineer, Threat Modeler, AI Security Engineer, Database Security Engineer, Privacy Engineer and Security QA Lead** for the existing Curavilo healthcare SaaS application.

Curavilo is a multi-tenant, AI-powered healthcare operating platform used by hospitals, clinics, specialist practices, diagnostic centres, laboratories, pharmacies and other healthcare facilities.

Curavilo may process highly sensitive information including:

* patient information
* clinical information
* appointments
* medical history
* prescriptions
* laboratory data
* imaging-related information
* staff information
* professional records
* financial transactions
* inventory information
* payment records
* operational data
* uploaded documents
* AI conversations
* audit records

This application must therefore be treated as a **high-security, security-sensitive healthcare SaaS system**.

Your task is to perform a complete security assessment of the existing Curavilo application and then harden it against realistic attacks across:

* frontend
* backend
* database
* authentication
* authorization
* sessions
* APIs
* files/storage
* third-party integrations
* payments
* messaging
* AI agents
* workflow engine
* document generation
* printing
* exports
* background jobs
* infrastructure
* deployment
* dependencies
* supply chain
* insider threats
* data leakage
* abuse
* denial of service
* configuration errors
* operational failures

DO NOT assume the existing application is secure simply because authentication exists, RLS exists, TypeScript compiles, or the UI hides restricted buttons.

The standard is:

> **Assume every client-side control can be bypassed. Assume every endpoint will eventually be probed. Assume every user input is hostile. Assume AI output is untrusted. Assume third-party systems can fail or become compromised. Assume an attacker will try to cross tenant boundaries.**

The objective is to build **defense in depth**.

# 11. IDOR / BOLA PROTECTION

Treat every object-ID endpoint as a potential Broken Object Level Authorization vulnerability.

For every endpoint/action:

```text id="5e4v4b"
GET /patients/:id
GET /reports/:id
GET /invoices/:id
GET /files/:id
POST /payments/:id/refund
PATCH /staff/:id
DELETE /workflow/:id
```

verify object authorization server-side.

Do NOT rely on:

* hidden UI elements
* UUID unpredictability
* route protection alone
* client-side role checks

Even if IDs are UUIDs, authorization is still mandatory.

OWASP specifically identifies Broken Object Level Authorization as the first API Security Top 10 risk.

# 12. BROKEN FUNCTION LEVEL AUTHORIZATION

Every privileged function must have explicit permission checks.

# 13. BROKEN PROPERTY LEVEL AUTHORIZATION

Do not only authorize the object.

Authorize sensitive fields too.

Example:

A staff object might contain:

```text id="b8zq3j"
name
department
role
phone
email
salary
bankAccount
employmentNotes
```

A user may be allowed to view the staff record but not:

* salary
* bank data
* private HR notes

Return DTOs containing only fields the user is permitted to receive.

Next.js guidance explicitly recommends a Data Access Layer and DTOs so sensitive data is not casually returned to the client.

# 24. PASSWORD SECURITY

Passwords must:

* never be stored plaintext
* never be logged
* never be returned through APIs
* never be placed in URLs
* never be included in analytics

If Curavilo itself stores passwords outside Supabase Auth for a legitimate architectural reason, use a modern password hashing scheme such as Argon2id with parameters appropriate to the deployment environment.

Do not use SHA-256 alone for passwords.

OWASP currently recommends Argon2id as the preferred modern password-storage approach.

Prefer letting Supabase Auth handle user passwords rather than inventing another password store.

# 227. MOST IMPORTANT PRINCIPLE

Never confuse:

> **"The frontend doesn't show it."**

with:

> **"The user cannot do it."**

Security exists only when the backend/database/infrastructure actually prevents the action.

---

# 228. SECOND MOST IMPORTANT PRINCIPLE

Never confuse:

> **"The AI was instructed not to do it."**

with:

> **"The system prevents it."**

AI safety must be enforced with:

* authorization
* tool restrictions
* server-side validation
* tenant isolation
* deterministic business rules
* human approval

The model itself is not the security boundary.

---

# 229. THIRD MOST IMPORTANT PRINCIPLE

Never confuse:

> **"We tested the happy path."**

with:

> **"We tested security."**

For every major feature ask:

> What happens when an attacker changes the ID?

> What happens when the role is forged?

> What happens when the request is repeated?

> What happens when the request is huge?

> What happens when data contains malicious instructions?

> What happens when a third-party system lies?

> What happens when a session is stolen?

> What happens when the user should not have access?

> What happens when two users act simultaneously?

> What happens when the database operation partially fails?

---

# 230. FINAL EXECUTION INSTRUCTION

Do not immediately start randomly editing files.

First inspect the entire Curavilo application.

Then:

1. produce the threat model
2. identify the highest-risk vulnerabilities
3. prioritize Critical and High issues
4. fix architectural vulnerabilities before cosmetic hardening
5. implement defense in depth
6. create security regression tests
7. run adversarial testing
8. run static/dependency/security tooling
9. review the final architecture
10. document remaining risks

Do not rewrite working functionality unnecessarily.

Do not replace the authentication system merely for the sake of change.

Do not disable security controls because they cause development inconvenience.

Do not suppress scanner results without investigation.

Do not claim production readiness without evidence.

The final objective is:

> **Curavilo must fail safely, deny unauthorized access by default, isolate every healthcare facility from every other facility, minimize sensitive-data exposure, treat AI as an untrusted component, protect financial and clinical operations, detect suspicious behavior, and provide a tested path to recovery when prevention fails.**
