# CURAVILO ENHANCEMENT

## Multi-Level Facility Access, Personnel Accounts, Role-Based Dashboards and Permissions

You are working inside the existing Curavilo healthcare SaaS codebase.

Do NOT rebuild the application from scratch.

First inspect the current implementation, architecture, authentication system, database schema, organization/facility model, roles, navigation, dashboards, permissions and existing onboarding flow.

Then enhance the existing system to implement the requirements below while preserving existing functionality.

The objective is to introduce a secure, production-quality personnel identity and role-based access architecture where every healthcare facility can create individual staff accounts and every staff member receives a dashboard and permissions based on their assigned role.

---

# 1. CORE REQUIREMENT

After a healthcare organization/facility registers on Curavilo, the facility owner must be able to:

1. Configure the facility.
2. Register/add personnel/staff members.
3. Assign each personnel member a role.
4. Create or invite each personnel member's individual account.
5. Give each personnel member their own login credentials.
6. Control exactly what that personnel member can access.
7. Allow every personnel member to access a dashboard customized for their assigned role.

The owner is the highest-authority user within the facility.

The owner must have access to all Curavilo functionality available to that facility.

Every other user must only see and access the functionality permitted by their assigned role and permissions.

---

# 2. IMPORTANT AUTHENTICATION MODEL

Implement a two-stage facility access experience.

Conceptually:

```text
                 CURAVILO LOGIN
                       ↓
             FACILITY ACCESS GATE
                       ↓
              Staff / Personnel Gate
                       ↓
            Role-Specific Dashboard
```

However, treat the two stages correctly from a security perspective.

The first stage identifies the facility/workspace.

The second stage identifies the individual person and determines their authorization.

The facility-level credential MUST NOT determine staff permissions.

The individual personnel account MUST determine access.

# 3. STAGE ONE: FACILITY ACCESS GATEWAY

Create a facility access gateway.

The initial screen should allow the user to enter:

```text
Facility Email
Facility Password
```

Example:

```text
┌──────────────────────────────────────┐
│              CURAVILO                │
│                                      │
│        Access Your Facility          │
│                                      │
│ Facility Email                       │
│ [________________________________]   │
│                                      │
│ Facility Password                    │
│ [________________________________]   │
│                                      │
│           [Continue]                 │
└──────────────────────────────────────┘
```

The facility password is a workspace/facility access credential.

It is NOT the same thing as a staff member's personal password.

Do not use the facility credential to assign permissions.

Do not use the facility credential as the staff identity.

---

# 4. SECURITY REQUIREMENT FOR FACILITY CREDENTIALS

Do not implement the facility credential as a plaintext password stored in the database.

Use secure password hashing through the authentication system.

Do not expose the facility password anywhere in the application.

Only the facility owner should be allowed to:

* create it
* change it
* reset it

If the existing architecture uses an identity provider that does not support a shared facility credential cleanly, create a secure facility-access abstraction rather than compromising the main authentication architecture.

Document the architectural decision.

---

# 5. STAGE TWO: PERSONNEL ACCESS GATEWAY

After successful facility authentication, DO NOT automatically show the main application dashboard.

Instead, display a second gateway for individual personnel authentication.

Example:

```text
┌──────────────────────────────────────┐
│       [FACILITY LOGO]               │
│                                      │
│     Access Your Staff Account        │
│                                      │
│ Name or Email                        │
│ [________________________________]   │
│                                      │
│ Password                             │
│ [________________________________]   │
│                                      │
│            [Sign In]                 │
│                                      │
│ Forgot Password?                     │
└──────────────────────────────────────┘
```

The person may authenticate using:

* email
* username, if supported

Do not require the user to literally enter their display name unless the system explicitly supports unique usernames.

Prefer email/username over unrestricted name matching because names are not guaranteed to be unique.

# 31. FACILITY LOGOUT VS STAFF LOGOUT

Design sessions carefully.

When staff logs out:

* their individual authenticated session must terminate
* their protected data must no longer be accessible

For the facility gateway session, use an appropriate secure short-lived session/context mechanism.

Do not leave an indefinitely valid facility authorization in the browser.

On shared computers, provide a clear:

> **Exit Facility**

option that fully clears facility access context.

This is important because multiple staff may use the same workstation during a shift.

# 34. AI AGENT PERMISSIONS

This requirement is extremely important.

The AI agent must inherit the authenticated staff member's permissions.

For example:

A receptionist asks:

> "Show me Dr. John's salary."

The AI must reject the request because the user's permissions do not allow access.

A doctor asks:

> "Summarize this patient's latest encounters."

The AI may retrieve permitted patient data.

A pharmacy staff member asks:

> "Show me all patients in the hospital."

The AI must restrict the query according to the user's permissions.

AI authorization must happen before data retrieval.

Never rely on the AI prompt alone.

# 69. EXPORT / PRINT PERMISSIONS

The existence of a report does not automatically mean every staff member can print/export it.

Authorization must apply to:

* view
* generate
* print
* download
* export
* reprint

Example:

A pharmacy worker may print a pharmacy receipt.

They may not automatically export the entire organization's revenue report.

# 70. FILE/DOCUMENT PERMISSIONS

The same role model must protect uploaded documents.

# 71. WORKFLOW PERMISSIONS

The role model must control:

* view workflow
* create workflow
* edit workflow
* test workflow
* publish workflow
* execute privileged workflow actions

The owner has full workflow administration.

Other staff get only what their permissions allow.

# 72. AI ACTION PERMISSIONS

The AI must not create a privilege escalation path.

If a receptionist cannot:

```text refund payment
```

through the normal UI/API, the AI must also be unable to perform that action.

The rule must be:

```text
AI action permissions ⊆ normal application permissions
```
