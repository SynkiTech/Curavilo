     1→# CURAVILO ENHANCEMENT
     2→
     3→## Multi-Level Facility Access, Personnel Accounts, Role-Based Dashboards and Permissions
     4→
     5→You are working inside the existing Curavilo healthcare SaaS codebase.
     6→
     7→Do NOT rebuild the application from scratch.
     8→
     9→First inspect the current implementation, architecture, authentication system, database schema, organization/facility model, roles, navigation, dashboards, permissions and existing onboarding flow.
    10→
    11→Then enhance the existing system to implement the requirements below while preserving existing functionality.
    12→
    13→The objective is to introduce a secure, production-quality personnel identity and role-based access architecture where every healthcare facility can create individual staff accounts and every staff member receives a dashboard and permissions based on their assigned role.
    14→
    15→---
    16→
    17→# 1. CORE REQUIREMENT
    18→
    19→After a healthcare organization/facility registers on Curavilo, the facility owner must be able to:
    20→
    21→1. Configure the facility.
    22→2. Register/add personnel/staff members.
    23→3. Assign each personnel member a role.
    24→4. Create or invite each personnel member's individual account.
    25→5. Give each personnel member their own login credentials.
    26→6. Control exactly what that personnel member can access.
    27→7. Allow every personnel member to access a dashboard customized for their assigned role.
    28→
    29→The owner is the highest-authority user within the facility.
    30→
    31→The owner must have access to all Curavilo functionality available to that facility.
    32→
    33→Every other user must only see and access the functionality permitted by their assigned role and permissions.
    34→
    35→---
    36→
    37→# 2. IMPORTANT AUTHENTICATION MODEL
    38→
    39→Implement a two-stage facility access experience.
    40→
    41→Conceptually:
    42→
    43→```text
    44→                 CURAVILO LOGIN
    45→                       ↓
    46→             FACILITY ACCESS GATE
    47→                       ↓
    48→              Staff / Personnel Gate
    49→                       ↓
    50→            Role-Specific Dashboard
    51→```
    52→
    53→However, treat the two stages correctly from a security perspective.
    54→
    55→The first stage identifies the facility/workspace.
    56→
    57→The second stage identifies the individual person and determines their authorization.
    58→
    59→The facility-level credential MUST NOT determine staff permissions.
    60→
    61→The individual personnel account MUST determine access.
    62→
    63→---
    64→
    65→# 3. STAGE ONE: FACILITY ACCESS GATEWAY
    66→
    67→Create a facility access gateway.
    68→
    69→The initial screen should allow the user to enter:
    70→
    71→```text
    72→Facility Email
    73→Facility Password
    74→```
    75→
    76→Example:
    77→
    78→```text
    79→┌──────────────────────────────────────┐
    80→│              CURAVILO                │
    81→│                                      │
    82→│        Access Your Facility          │
    83→│                                      │
    84→│ Facility Email                       │
    85→│ [________________________________]   │
    86→│                                      │
    87→│ Facility Password                    │
    88→│ [________________________________]   │
    89→│                                      │
    90→│           [Continue]                 │
    91→└──────────────────────────────────────┘
    92→```
    93→
    94→The facility password is a workspace/facility access credential.
    95→
    96→It is NOT the same thing as a staff member's personal password.
    97→
    98→Do not use the facility credential to assign permissions.
    99→
   100→Do not use the facility credential as the staff identity.
   101→
   102→---
   103→
   104→# 4. SECURITY REQUIREMENT FOR FACILITY CREDENTIALS
   105→
   106→Do not implement the facility credential as a plaintext password stored in the database.
   107→
   108→Use secure password hashing through the authentication system.
   109→
   110→Do not expose the facility password anywhere in the application.
   111→
   112→Only the facility owner should be allowed to:
   113→
   114→* create it
   115→* change it
   116→* reset it
   117→
   118→If the existing architecture uses an identity provider that does not support a shared facility credential cleanly, create a secure facility-access abstraction rather than compromising the main authentication architecture.
   119→
   120→Document the architectural decision.
   121→
   122→---
   123→
   124→# 5. STAGE TWO: PERSONNEL ACCESS GATEWAY
   125→
   126→After successful facility authentication, DO NOT automatically show the main application dashboard.
   127→
   128→Instead, display a second gateway for individual personnel authentication.
   129→
   130→Example:
   131→
   132→```text
   133→┌──────────────────────────────────────┐
   134→│       [FACILITY LOGO]               │
   135→│                                      │
   136→│     Access Your Staff Account        │
   137→│                                      │
   138→│ Name or Email                        │
   139→│ [________________________________]   │
   140→│                                      │
   141→│ Password                             │
   142→│ [________________________________]   │
   143→│                                      │
   144→│            [Sign In]                 │
   145→│                                      │
   146→│ Forgot Password?                     │
   147→└──────────────────────────────────────┘
   148→```
   149→
   150→The person may authenticate using:
   151→
   152→* email
   153→* username, if supported
   154→
   155→Do not require the user to literally enter their display name unless the system explicitly supports unique usernames.
   156→
   157→Prefer email/username over unrestricted name matching because names are not guaranteed to be unique.

   198→# 7. STAFF ONBOARDING
   199→
   200→The owner should have a clear workflow:
   201→
   202→```text
   203→Owner Dashboard
   204→      ↓
   205→Staff / Personnel
   206→      ↓
   207→Add Staff
   208→      ↓
   209→Enter Staff Details
   210→      ↓
   211→Choose Role
   212→      ↓
   213→Choose Department
   214→      ↓
   215→Choose Service Line
   216→      ↓
   217→Create / Invite Account
   218→      ↓
   219→Staff Can Log In
   220→```
   221→
   222→Provide two secure account-creation approaches:
   223→
   224→### Option A: Invitation
   225→
   226→Preferred for production.
   227→
   228→Owner enters the staff member's email.
   229→
   230→Curavilo sends an invitation.
   231→
   232→The staff member establishes their own password.
   233→
   234→### Option B: Owner-created temporary password
   235→
   236→Useful for environments where invitation email may not be reliable.
   237→
   238→The owner can generate a temporary password.
   239→
   240→The staff member must be forced to change it at first login.
   241→
   242→Never display permanent passwords in logs.
   243→
   244→Never expose passwords after creation.
   245→
   246→Never store plaintext passwords.

   253→
   254→Do NOT make the shared facility credentials the owner's permanent identity.

   256→The owner should have:
   257→
   258→```text
   259→Facility Access
   260→+
   261→Owner Personal Account
   262→```
   263→
   264→The owner's personal account should have the highest permission level.
   265→
   266→The owner can:
   267→
   268→* manage facility
   269→* manage staff
   270→* assign roles
   271→* modify permissions
   272→* configure services
   273→* configure departments
   274→* configure workflows
   275→* access patients where permitted by facility policy
   276→* access billing
   277→* access POS
   278→* access pharmacy
   279→* access inventory
   280→* access reports
   281→* use AI
   282→* access analytics
   283→* access simulation
   284→* access settings
   285→* manage branding
   286→* manage facility credentials
   287→* manage subscriptions/features
   288→* view audit logs
   289→
   290→The owner is the only built-in role with unrestricted facility-level administrative access.
   291→
   292→Do not create another ordinary staff role that automatically has the same privileges as OWNER.

   857→# 31. FACILITY LOGOUT VS STAFF LOGOUT
   858→
   859→Design sessions carefully.
   860→
   861→When staff logs out:
   862→
   863→* their individual authenticated session must terminate
   864→* their protected data must no longer be accessible
   865→
   866→For the facility gateway session, use an appropriate secure short-lived session/context mechanism.
   867→
   868→Do not leave an indefinitely valid facility authorization in the browser.

   871→
   872→> **Exit Facility**
   873→
   874→option that fully clears facility access context.

   920→# 34. AI AGENT PERMISSIONS
   921→
   922→This requirement is extremely important.
   923→
   924→The AI agent must inherit the authenticated staff member's permissions.
   925→
   926→For example:
   927→
   928→A receptionist asks:
   929→
   930→> "Show me Dr. John's salary."
   931→
   932→The AI must reject the request because the user's permissions do not allow access.
   933→
   934→A doctor asks:
   935→
   936→> "Summarize this patient's latest encounters."
   937→
   938→The AI may retrieve permitted patient data.
   939→
   940→A pharmacy staff member asks:
   941→
   942→> "Show me all patients in the hospital."
   943→
   944→The AI must restrict the query according to the user's permissions.
   945→
   946→AI authorization must happen before data retrieval.
   947→
   948→Never rely on the AI prompt alone.
   949→
