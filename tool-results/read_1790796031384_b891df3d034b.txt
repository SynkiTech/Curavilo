    83→    83→# 2. CORE PRODUCT PRINCIPLES
    84→    84→
    85→    85→These are non-negotiable.
    86→    86→
    87→    87→## 2.1 Configuration over hard-coding
    88→    88→
    89→    89→Do not hard-code one hospital's workflow into the core application.
    90→    90→
    91→    91→Curavilo must support different healthcare facility types using configurable service profiles.
    92→    92→
    93→    93→## 2.2 One source of truth
    94→    94→
    95→    95→Patient, staff, inventory, financial, appointment, workflow and operational data must originate from the application's canonical data model.
    96→    96→
    97→    97→Do not create disconnected shadow databases for individual features unless there is a documented architectural reason.
    98→    98→
    99→    99→## 2.3 Deterministic core, probabilistic AI
   100→   100→
   101→   101→Business-critical operations must be deterministic.
   102→   102→
   103→   103→Examples:
   104→   104→
   105→   105→* Billing calculations
   106→   106→* Inventory quantities
   107→   107→* Payment records
   108→   108→* Workflow state transitions
   109→   109→* Permissions
   110→   110→* Audit logs
   111→   111→* Patient identifiers
   112→   112→* Report totals
   113→   113→* Receipt totals
   114→   114→
   115→   115→AI can interpret, summarize, suggest, classify and assist, but it must not become the source of truth for deterministic business rules.
   116→   116→
   117→   117→## 2.4 Permission before retrieval
   118→   118→
   119→   119→Never let the AI retrieve information first and check permissions afterward.
   120→   120→
   121→   121→Authorization must happen before protected data is exposed to the model.
   122→   122→
   123→   123→## 2.5 No hallucinated database answers
   124→   124→
   125→   125→For questions about Curavilo data:
   126→   126→
   127→   127→* query the actual authorized data
   128→   128→* calculate deterministically
   129→   129→* return grounded results
   130→   130→* show relevant provenance
   131→   131→* say when the data is unavailable, ambiguous or incomplete
   132→   132→
   133→   133→Never invent values.
   134→   134→
   135→   135→## 2.6 Human control over high-risk actions
   136→   136→
   137→   137→The AI may eventually perform actions, but high-impact actions require deterministic authorization and appropriate human confirmation.
   138→   138→
   139→   139→The model must never be the final authority over:
   140→   140→
   141→   141→* refunds
   142→   142→* deleting sensitive records
   143→   143→* changing permissions
   144→   144→* bulk exports
   145→   145→* modifying financial records
   146→   146→* publishing high-impact workflows
   147→   147→* altering important clinical records
   148→   148→* sending large-scale patient communications
   149→   149→* other irreversible or high-risk actions
   150→   150→
   151→   151→## 2.7 Privacy by design
   152→   152→
   153→   153→Privacy and security must exist in the architecture from the beginning.
   154→   154→
   155→   155→Do not build first and "secure it later."
   156→   156→
   157→   157→## 2.8 Modular monolith first
   158→   158→
   159→   159→Build one well-structured application with clearly separated domain modules.
   160→   160→
   161→   161→Do not introduce microservices merely because the product is large.
   162→   162→
   163→   163→Only split infrastructure later when scale, reliability or ownership boundaries actually justify it.
   164→   164→
   165→   165→## 2.9 Every important operation must be auditable
   166→   166→
   167→   167→We need to know:
   168→   168→
   169→   169→* who did it
   170→   170→* what they did
   171→   171→* what record was affected
   172→   172→* when it happened
   173→   173→* what changed
   174→   174→* which organization/facility it belonged to
   175→   175→* where appropriate, which workflow, document or AI action caused it
   176→   176→
   177→   177→Never log sensitive data unnecessarily.
   178→   178→

   182→   182→
   183→   183→Follow this development loop throughout the project:
   184→   184→
   185→   185→```text
   186→   186→EXPLORE
   187→   187→   ↓
   188→   188→UNDERSTAND
   189→   189→   ↓
   190→   190→PLAN
   191→   191→   ↓
   192→   192→IMPLEMENT
   193→   193→   ↓
   194→   194→TEST
   195→   195→   ↓
   196→   196→VERIFY
   197→   197→   ↓
   198→   198→ADVERSARIAL REVIEW
   199→   199→   ↓
   200→   200→DOCUMENT
   201→   201→   ↓
   202→   202→COMMIT
   203→   203→```
   204→   204→
   205→   205→For any non-trivial feature:
   206→   206→
   207→   207→1. Explore the existing codebase and relevant architecture first.
   208→   208→2. Determine the correct files/modules that should change.
   209→   209→3. Produce a concise implementation plan.
   210→   210→4. Implement in small coherent slices.
   211→   211→5. Run relevant tests immediately.
   212→   212→6. Run linting and type checking.
   213→   213→7. Build the application.
   214→   214→8. For UI work, verify visually in a real browser.
   215→   215→9. Run an adversarial review using an appropriate subagent.
   216→   216→10. Fix discovered issues.
   217→   217→11. Document important decisions.
   218→   218→12. Commit the coherent milestone.
   219→   219→
   220→   220→Never claim a feature is complete without evidence.
   221→   221→
   222→   222→Evidence may include:
   223→   223→
   224→   224→* successful tests
   225→   225→* build output
   226→   226→* lint output
   227→   227→* type-check output
   228→   228→* integration test output
   229→   229→* browser verification
   230→   230→* screenshots

   322→   322→2. Check git status.

   324→   324→4. Inspect `package.json`.
   325→   325→5. Inspect existing framework versions.
   326→   326→6. Inspect environment configuration.
   327→   327→7. Inspect database configuration.
   328→   328→8. Inspect existing docs.
   329→   329→9. Inspect current folder structure.
   330→   330→10. Identify whether the repository is empty, partially built or already contains an application.
   331→   331→11. Check installed versions against current official documentation.
   332→   332→12. Do not blindly replace working configuration.
   333→   333→13. Do not delete or overwrite existing code unless there is a documented reason.
   334→   334→
   335→   335→If the repository is empty, initialize the project using the agreed architecture.
   336→   336→

   510→   510→# 9. MULTI-TENANCY
   511→   511→
   512→   512→Curavilo is multi-tenant.
   513→   513→
   514→   514→Top-level conceptual model:
   515→   515→
   516→   516→```text
   517→   517→Organization
   518→   518→   │
   519→   519→   ├── Facilities
   520→   520→   │     ├── Departments
   521→   521→   │     ├── Service Lines
   522→   522→   │     ├── Staff
   523→   523→   │     ├── Patients
   524→   524→   │     ├── Workflows
   525→   525→   │     ├── Inventory
   526→   526→   │     └── Transactions
   527→   527→   │
   528→   528→   └── Subscription
   529→   529→```
   530→   530→
   531→   531→A single organization may own multiple healthcare facilities or branches.
   532→   532→
   533→   533→All organization-owned records must be tenant-scoped.
   534→   534→
   535→   535→Do not trust `organizationId`, `facilityId` or similar identifiers supplied by the browser without server-side verification.
   536→   536→
   537→   537→Every privileged operation must derive tenant scope from authenticated membership.
   538→   538→
   539→   539→Implement:
   540→   540→
   541→   541→* organization isolation
   542→   542→* facility isolation
   543→   543→* branch/facility scoping
   544→   544→* role permissions
   545→   545→* service-line permissions
   546→   546→* department permissions where applicable
   547→   547→* field-level restrictions for highly sensitive information
   548→   548→
   549→   549→Use database-level row-level security where the access path supports it, as defense in depth.
   550→   550→
   551→   551→Do not assume RLS alone is sufficient if an ORM/service connection bypasses it.
   552→   552→
   553→   553→Build automated cross-tenant tests that attempt:
   554→   554→
   555→   555→* read another tenant's patient
   556→   556→* update another tenant's patient
   557→   557→* access another tenant's inventory
   558→   558→* view another tenant's report
   559→   559→* use another tenant's AI context
   560→   560→* retrieve another tenant's files
   561→   561→* execute another tenant's workflow
   562→   562→
   563→   563→All must fail securely.
   564→   564→
