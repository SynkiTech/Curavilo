     1→     1→# CURAVILO ENHANCEMENT
     2→     2→
     3→     3→## Multi-Level Facility Access, Personnel Accounts, Role-Based Dashboards and Permissions
     4→     4→
     5→     5→You are working inside the existing Curavilo healthcare SaaS codebase.
     6→     6→
     7→     7→Do NOT rebuild the application from scratch.
     8→     8→
     9→     9→First inspect the current implementation, architecture, authentication system, database schema, organization/facility model, roles, navigation, dashboards, permissions and existing onboarding flow.
    10→    10→
    11→    11→Then enhance the existing system to implement the requirements below while preserving existing functionality.
    12→    12→
    13→    13→The objective is to introduce a secure, production-quality personnel identity and role-based access architecture where every healthcare facility can create individual staff accounts and every staff member receives a dashboard and permissions based on their assigned role.
    14→    14→
    15→    15→---
    16→    16→
    17→    17→# 1. CORE REQUIREMENT
    18→    18→
    19→    19→After a healthcare organization/facility registers on Curavilo, the facility owner must be able to:
    20→    20→
    21→    21→1. Configure the facility.
    22→    22→2. Register/add personnel/staff members.
    23→    23→3. Assign each personnel member a role.
    24→    24→4. Create or invite each personnel member's individual account.
    25→    25→5. Give each personnel member their own login credentials.
    26→    26→6. Control exactly what that personnel member can access.
    27→    27→7. Allow every personnel member to access a dashboard customized for their assigned role.
    28→    28→
    29→    29→The owner is the highest-authority user within the facility.
    30→    30→
    31→    31→The owner must have access to all Curavilo functionality available to that facility.
    32→    32→
    33→    33→Every other user must only see and access the functionality permitted by their assigned role and permissions.
    34→    34→
    35→    35→---
    36→    36→
    37→    37→# 2. IMPORTANT AUTHENTICATION MODEL
    38→    38→
    39→    39→Implement a two-stage facility access experience.
    40→    40→
    41→    41→Conceptually:
    42→    42→
    43→    43→```text
    44→    44→                 CURAVILO LOGIN
    45→    45→                       ↓
    46→    46→             FACILITY ACCESS GATE
    47→    47→                       ↓
    48→    48→              Staff / Personnel Gate
    49→    49→                       ↓
    50→    50→            Role-Specific Dashboard
    51→    51→```
    52→    52→
    53→    53→However, treat the two stages correctly from a security perspective.
    54→    54→
    55→    55→The first stage identifies the facility/workspace.
    56→    56→
    57→    57→The second stage identifies the individual person and determines their authorization.
    58→    58→
    59→    59→The facility-level credential MUST NOT determine staff permissions.
    60→    60→
    61→    61→The individual personnel account MUST determine access.
    62→    62→
    63→    63→---
    64→    64→
    65→    65→# 3. STAGE ONE: FACILITY ACCESS GATEWAY
    66→    66→
    67→    67→Create a facility access gateway.
    68→    68→
    69→    69→The initial screen should allow the user to enter:
    70→    70→
    71→    71→```text
    72→    72→Facility Email
    73→    73→Facility Password
    74→    74→```
    75→    75→
    76→    76→Example:
    77→    77→
    78→    78→```text
    79→    79→┌──────────────────────────────────────┐
    80→    80→│              CURAVILO                │
    81→    81→│                                      │
    82→    82→│        Access Your Facility          │
    83→    83→│                                      │
    84→    84→│ Facility Email                       │
    85→    85→│ [________________________________]   │
    86→    86→│                                      │
    87→    87→│ Facility Password                    │
    88→    88→│ [________________________________]   │
    89→    89→│                                      │
    90→    90→│           [Continue]                 │
    91→    91→└──────────────────────────────────────┘
    92→    92→```
    93→    93→
    94→    94→The facility password is a workspace/facility access credential.
    95→    95→
    96→    96→It is NOT the same thing as a staff member's personal password.
    97→    97→
    98→    98→Do not use the facility credential to assign permissions.
    99→    99→
   100→   100→Do not use the facility credential as the staff identity.
   101→   101→
   102→   102→---
   103→   103→
   104→   104→# 4. SECURITY REQUIREMENT FOR FACILITY CREDENTIALS
   105→   105→
   106→   106→Do not implement the facility credential as a plaintext password stored in the database.
   107→   107→
   108→   108→Use secure password hashing through the authentication system.
   109→   109→
   110→   110→Do not expose the facility password anywhere in the application.
   111→   111→
   112→   112→Only the facility owner should be allowed to:
   113→   113→
   114→   114→* create it
   115→   115→* change it
   116→   116→* reset it
   117→   117→
   118→   118→If the existing architecture uses an identity provider that does not support a shared facility credential cleanly, create a secure facility-access abstraction rather than compromising the main authentication architecture.
   119→   119→
   120→   120→Document the architectural decision.
   121→   121→
   122→   122→---
   123→   123→
   124→   124→# 5. STAGE TWO: PERSONNEL ACCESS GATEWAY
   125→   125→
   126→   126→After successful facility authentication, DO NOT automatically show the main application dashboard.
   127→   127→
   128→   128→Instead, display a second gateway for individual personnel authentication.
   129→   129→
   130→   130→Example:
   131→   131→
   132→   132→```text
   133→   133→┌──────────────────────────────────────┐
   134→   134→│       [FACILITY LOGO]               │
   135→   135→│                                      │
   136→   136→│     Access Your Staff Account        │
   137→   137→│                                      │
   138→   138→│ Name or Email                        │
   139→   139→│ [________________________________]   │
   140→   140→│                                      │
   141→   141→│ Password                             │
   142→   142→│ [________________________________]   │
   143→   143→│                                      │
   144→   144→│            [Sign In]                 │
   145→   145→│                                      │
   146→   146→│ Forgot Password?                     │
   147→   147→└──────────────────────────────────────┘
   148→   148→```
   149→   149→
   150→   150→The person may authenticate using:
   151→   151→
   152→   152→* email
   153→   153→* username, if supported
   154→   154→
   155→   155→Do not require the user to literally enter their display name unless the system explicitly supports unique usernames.
   156→   156→
   157→   157→Prefer email/username over unrestricted name matching because names are not guaranteed to be unique.
   158→   158→

   220→   220→```
   221→   221→
   222→   222→Provide two secure account-creation approaches:
   223→   223→
   224→   224→### Option A: Invitation
   225→   225→
   226→   226→Preferred for production.
   227→   227→
   228→   228→Owner enters the staff member's email.
   229→   229→
   230→   230→Curavilo sends an invitation.
   231→   231→
   232→   232→The staff member establishes their own password.
   233→   233→
   234→   234→### Option B: Owner-created temporary password
   235→   235→
   236→   236→Useful for environments where invitation email may not be reliable.
   237→   237→
   238→   238→The owner can generate a temporary password.
   239→   239→
   240→   240→The staff member must be forced to change it at first login.
   241→   241→
   242→   242→Never display permanent passwords in logs.
   243→   243→
   244→   244→Never expose passwords after creation.
   245→   245→
   246→   246→Never store plaintext passwords.
   247→   247→

   936→   936→> "Summarize this patient's latest encounters."

   938→   938→The AI may retrieve permitted patient data.

   940→   940→A pharmacy staff member asks:
